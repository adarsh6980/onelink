# OneLink - receipt intake and splitting

Two flows, one small app, no accounts on either side:

1. **Intake**: a bookkeeper (or team lead) creates a request and hands out one
   upload link. People drop receipt photos; the app reads vendor, date, total,
   VAT and the item lines, and only human-reviewed uploads reach the CSV export.
2. **Split**: drop a receipt, tick who each item belongs to (or split equally),
   and the app does the integer-cent arithmetic: who paid, who owes whom.

Everything runs on one server you control. Receipt photos and line items are processed there and are never sent to an external model API or third-party service.

## Extraction engines

Every photo is read by two independent local engines and the better parse wins
(recovered item count dominates, then total confidence, then OCR confidence):

- **RapidOCR** (neural): PP-OCRv4 detection/recognition ONNX models via the
  `rapidocr-onnxruntime` pip package. Runs on CPU, no network, no account.
- **Tesseract** (classical): system `tesseract`, with a grayscale/sharpen
  preprocessing rescue pass used only when the first read is weak.

The engine that produced each extraction is labelled in the UI
(`rapidocr-local` / `tesseract-local`).

## Receipts are read, never trusted

OCR of any engine makes mistakes, so a split or export only becomes final when:

1. every item is assigned (for splits),
2. the items add up to the receipt total exactly,
3. a person has explicitly confirmed the receipt total and that the item list
   is complete. Matching sums alone do not prove the read was complete; no
   engine confidence skips this check.

Amounts that needed OCR repair are flagged for review instead of silently
fixed. Discount-looking lines read as positive get a sign warning. Any edit
invalidates the confirmation and it must be confirmed again. The AI never
decides who owns an item and never computes the split; people choose ownership,
deterministic code does the arithmetic.

## Running it

Requires Node.js 18+; optionally Python 3.10+ for the neural engine and
Tesseract for the classical one.

    pip install rapidocr-onnxruntime   # neural engine (optional but recommended)
    node server.js                     # serves on http://localhost:8123
    bash scripts/demo.sh               # seeds a demo request with 8 generated samples
    bash scripts/test_hardening.sh     # security/correctness checks
    bash scripts/test_split.sh         # split-flow checks

All sample receipts under `scripts/samples/` are generated by the `make_*_samples.py`
scripts; no real receipts or personal data are in this repository.

## Deployment on Vultr

The app is a single Node.js process with local OCR engines and JSON file
storage, designed to run as the web backend on one Vultr Cloud Compute
instance (plan `vc2-1c-2gb`). Vultr hosts the whole system: the web app, the
extraction engines and the data. See DEPLOY.md for the runbook, including the
teardown path (destroying the instance ends all billing).

## Optional hosted model

Setting `AI_BASE_URL`, `AI_API_KEY` and `AI_MODEL` routes extraction through an
OpenAI-compatible vision endpoint instead (with `AI_MAX_REQUESTS` as an
application-level request cap - not a provider spend cap). Off by default; the
local engines above need nothing.

## Honest limits

OCR can misread photos, especially skewed or low-light ones. On a real
supermarket receipt photo the current build recovered every line and the exact
total, but still needed a person to fix two discount signs. Treat every
extraction as a draft until a person confirms it. Not financial advice.
